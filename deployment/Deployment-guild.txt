================================================================================
FairShareMon — Production Deployment Guide
================================================================================

This deploys the full stack with Docker Compose:

    [ upstream: TLS + tunnel/proxy ]      (you provide — e.g. Cloudflare Tunnel
              |                            or a host reverse proxy; terminates
              v                            HTTPS and forwards Host + X-Forwarded-*)
        nginx (:80)  ── reverse proxy + rate limiting ──┐
          |  fairsharemon.minhkakart.com  -> web:5173   │
          |  fairsharemon-api...          -> api:8080   │
        fail2ban  ── tails nginx logs, bans via nginx deny-list
          api (:8080, .NET 8)  -> mariadb:3306, redis:6379
          web (:5173, static SPA)

All containers talk over the external Docker network `wsl-net`. nginx is NOT
published to the host; your upstream reaches it on that network over port 80 and
must terminate TLS and pass the real client IP in X-Forwarded-For.

--------------------------------------------------------------------------------
0. PREREQUISITES
--------------------------------------------------------------------------------
- A Linux / WSL2 host with Docker Engine + Docker Compose v2 (`docker compose`).
- An upstream that terminates HTTPS for the two subdomains and forwards to the
  nginx container on the `wsl-net` network, port 80, preserving the Host header
  and setting X-Forwarded-For / X-Forwarded-Proto (Cloudflare Tunnel, a host
  nginx, Traefik, etc.). nginx reads the real client IP from X-Forwarded-For.
- Two DNS records at your provider:
      fairsharemon.minhkakart.com        -> the upstream/tunnel
      fairsharemon-api.minhkakart.com    -> the upstream/tunnel

--------------------------------------------------------------------------------
1. GET THE CODE
--------------------------------------------------------------------------------
    git clone <repo-url> FairShareMon
    cd FairShareMon/deployment

--------------------------------------------------------------------------------
2. CONFIGURE  (two gitignored files — never commit either)
--------------------------------------------------------------------------------
2a. deployment/.env — service secrets used by Docker Compose:

    cp .env.example .env
    #    MARIADB_ROOT_PASSWORD  = a strong password  (SINGLE source: the mariadb container AND the
    #                                                 API's connection string, injected by compose)
    #    REDIS_PASSWORD         = a strong password  (SINGLE source: the redis container AND the API)
    #    VITE_API_BASE_URL      = https://fairsharemon-api.minhkakart.com (baked into the web build)
    #    ASPNETCORE_ENVIRONMENT = Production

2b. The API's app config — mounted read-only into the api container (NOT baked into the image):

        FairShareMonApi/FairShareMonApi/appsettings.Production.local.json

    Create this file on the host (copy the committed appsettings.json as a base) and set:
      App:AllowedOrigins           [ "https://fairsharemon.minhkakart.com" ]   (the web origin, for CORS)
      App:RunMigrationsOnStartup   true
      Admin:Username / Admin:Password   (optional; empty password => no admin seeded)
      ...plus any Auth / Tiers overrides you want.

    Do NOT put ConnectionStrings / Redis here — compose injects them from .env (env wins over the
    file), so the DB/Redis password lives in exactly one place (.env). Hosts are the compose service
    names (`mariadb`, `redis`).

    IMPORTANT: this file MUST EXIST before `docker compose up` — a missing bind-mount source makes
    Docker create a directory in its place and the API starts without config.

--------------------------------------------------------------------------------
3. CONFIRM THE DOMAINS IN NGINX
--------------------------------------------------------------------------------
If your domains differ from the defaults, edit the `server_name` lines:
    config/nginx/conf.d/web.conf   -> fairsharemon.minhkakart.com
    config/nginx/conf.d/api.conf   -> fairsharemon-api.minhkakart.com
(Optional) tighten the trusted-proxy range in config/nginx/nginx.conf
(`set_real_ip_from`) to your upstream's actual subnet.

--------------------------------------------------------------------------------
4. CREATE THE NETWORK AND DATA DIRECTORIES
--------------------------------------------------------------------------------
Either run the helper:

    ./run-before-compose-up.sh

...or run the equivalent commands manually:

    docker network inspect wsl-net >/dev/null 2>&1 || docker network create wsl-net
    mkdir -p data/blocked data/nginx/logs data/nginx/html \
             data/mariadb data/redis data/fail2ban

(On Linux/WSL, ensure the containers can write to ./data — they run as their
image users; `chmod`/`chown` the data dirs if you hit permission errors.)

--------------------------------------------------------------------------------
5. POINT YOUR UPSTREAM AT NGINX
--------------------------------------------------------------------------------
Configure the tunnel/host-proxy to forward both hostnames to the nginx container
on `wsl-net`, port 80, preserving Host and adding X-Forwarded-For/-Proto. Example
Cloudflare Tunnel ingress:
    - hostname: fairsharemon.minhkakart.com      service: http://nginx:80
    - hostname: fairsharemon-api.minhkakart.com  service: http://nginx:80
(Run cloudflared on the `wsl-net` network so `nginx` resolves.)

--------------------------------------------------------------------------------
6. PULL THE IMAGES AND BRING UP THE STACK
--------------------------------------------------------------------------------
The api and web images are built and pushed by CI (.github/workflows/ci.yml) —
this host only PULLS them. Set API_VERSION / WEB_VERSION in .env to the tags you
want (see RELEASING below), then:

    docker compose config          # sanity-check the merged config + .env
    docker compose pull            # fetch the published api/web images
    docker compose up -d

MariaDB creates the `fairsharemon` database on first boot (config/mariadb/
init_database.sql). The api waits for MariaDB + Redis to be healthy, then applies
the EF Core schema on startup if you enabled the flag (see A) — so `docker compose
up` is the whole deploy.

    Note: `docker compose up -d --build` also works, but it builds the images
    LOCALLY from the working tree and overwrites the tag you pulled — so you are no
    longer running the artifact CI tested and published. Use it only for local
    experiments, never on the deploy host.

================================================================================
AFTER THE FIRST BRING-UP
================================================================================

A) DATABASE SCHEMA — applied on startup, but ONLY IF YOU ENABLE IT
   The api applies EF Core migrations on startup when App:RunMigrationsOnStartup is
   true, from the migrations compiled into the image — so the schema is brought
   current by `docker compose up`, with no manual step, and a redeploy (see
   Operations) auto-applies any new migrations in a release.

   IMPORTANT: that flag is NOT set in docker-compose.yml, and the committed
   appsettings.json default is FALSE. You must set it yourself in the host-mounted

       FairShareMonApi/FairShareMonApi/appsettings.Production.local.json

   as instructed in step 2b:  "App": { "RunMigrationsOnStartup": true }
   (or add App__RunMigrationsOnStartup=true to the api service's environment).
   Leave it false and the api will start against an un-migrated database.

   SCALING: keep migrate-on-startup on a SINGLE api instance. EF has no
   cross-instance migration lock for MySQL — if you scale the api, apply
   migrations from one instance first, then run the rest with
   App__RunMigrationsOnStartup=false.

   Manual fallback (only if you disable auto-migrate) — generate an idempotent
   script and pipe it into MariaDB:
       cd ../FairShareMonApi
       dotnet ef migrations script --idempotent \
           --project FairShareMonApi/FairShareMonApi.csproj -o schema.sql
       cd ../deployment
       docker compose exec -T mariadb \
           mariadb -uroot -p"$MARIADB_ROOT_PASSWORD" fairsharemon < ../FairShareMonApi/schema.sql

B) VERIFY
       docker compose ps                         # all services Up / healthy
       docker compose exec nginx nginx -t        # nginx config OK
       # API health through nginx (simulating the upstream):
       curl -H 'Host: fairsharemon-api.minhkakart.com' \
            -H 'X-Forwarded-For: 203.0.113.9' \
            http://<host-or-nginx-ip>/api/v1/health     # -> 200
       # Real client IP is logged (not the proxy):
       tail -f data/nginx/logs/access.log
       # fail2ban jails are active:
       docker compose exec fail2ban fail2ban-client status
   Then browse https://fairsharemon.minhkakart.com and register/login.

================================================================================
RELEASING  (CI builds and publishes the images — see .github/workflows/ci.yml)
================================================================================
You never build api/web on a host any more. GitHub Actions builds both images and
pushes them to docker-registry.minhkakart.com. api and web are versioned
INDEPENDENTLY, so shipping one never re-tags the other.

What each git ref publishes:

    git push origin api-v1.4.0   ->  fairsharemon-api:1.4.0, :1.4, :latest, :sha-<sha>
    git push origin web-v2.1.0   ->  fairsharemon-web:2.1.0, :2.1, :latest, :sha-<sha>
    merge a PR into master       ->  :edge, :sha-<sha>        (never :latest)
    open a pull request          ->  image built, nothing pushed

So `latest` is always the newest deliberate RELEASE; `edge` is the tip of master.

Cutting a release:

    1. Merge to master. CI publishes :edge — smoke-test it on a staging host if you
       have one (set API_VERSION=edge / WEB_VERSION=edge there).
    2. Tag only what you actually shipped, semver, from master:
           git tag api-v1.4.0 && git push origin api-v1.4.0
           git tag web-v2.1.0 && git push origin web-v2.1.0
    3. On this host, set the version in .env and roll it out:
           docker compose pull && docker compose up -d
       (Or pin API_VERSION=latest / WEB_VERSION=latest to always take the newest
       release without editing .env — at the cost of not knowing what you run.)

Rollback: set the version in .env back to any previously published tag and re-pull.
Beware that a rollback does NOT revert database migrations — if the release you are
backing out added a migration, the old image runs against the newer schema.

Checking what a tag actually points at:

    docker buildx imagetools inspect docker-registry.minhkakart.com/fairsharemon-api:latest

Gates before a push happens — nothing is published unless the matching gate is green:
    web   `pnpm lint`, `pnpm build` (tsc -b), `pnpm test` (vitest)
    api   `dotnet test FairShareMonApi.sln`, run against throwaway mariadb:11.7 +
          redis:7.4 service containers that CI creates and destroys per run. CI
          never touches this host's database. Migrations are applied to the
          throwaway DB first (`dotnet ef database update`), because the test
          harness opens a transaction but does not create the schema.
Note the CI Redis has no password (GitHub service containers cannot take the
`--requirepass` argument this stack uses) — that only affects the test run, never
this deployment.

CI needs these configured once in GitHub → Settings → Secrets and variables:
    Variable  REGISTRY           = docker-registry.minhkakart.com
    Variable  VITE_API_BASE_URL  = https://fairsharemon-api.minhkakart.com
    Secret    REGISTRY_USERNAME  / REGISTRY_PASSWORD

Note: VITE_API_BASE_URL is inlined into the web bundle at BUILD time, so a web
image serves exactly one API origin and cannot be promoted between environments.

================================================================================
OPERATIONS
================================================================================
Logs:        docker compose logs -f api        (or nginx / web / mariadb / redis)
             data/nginx/logs/access.log        (fail2ban source)
fail2ban:    docker compose exec fail2ban fail2ban-client status fsm-auth-login
             ...unban:  fail2ban-client set fsm-auth-login unbanip <ip>
             live bans: data/blocked/banned.conf  (nginx auto-reloads ~10s)
Redeploy:    set API_VERSION / WEB_VERSION in .env to the tag you want, then
                 docker compose pull && docker compose up -d
             (auto-applies any new migrations on api startup when the flag in A is
             on). Do NOT use `--build` here — see the note in step 6.
Restart one: docker compose restart nginx
Tune limits: edit the zones in config/nginx/nginx.conf and the thresholds in
             data/fail2ban/jail.d/fairsharemon.conf, then `docker compose up -d`.
Backups:     back up data/mariadb (or use mysqldump), plus your .env.

================================================================================
NOTES
================================================================================
- Enforcement lives at nginx: rate-limits return 429 and fail2ban bans real IPs
  via an nginx deny-list (iptables can't see real IPs behind the tunnel).
- Balanced limits: API ~10 r/s, login/refresh ~20 r/min, register ~5/hour;
  bans last 1h. Adjust in the two files noted above.
- The API reads its config from appsettings.Production.local.json, mounted at
  runtime (gitignored + excluded from the image, so secrets are never baked in).
  The DB/Redis passwords live only in .env (single source) and compose injects
  them into the API's connection strings (env wins over the file). Any other key
  can also be overridden per-container with an env var.
